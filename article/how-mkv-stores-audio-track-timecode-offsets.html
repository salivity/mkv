How MKV Stores Audio Track Timecode Offsets

The Matroska (MKV) container handles misaligned secondary audio streams primarily by embedding relative timestamps directly into individual frame blocks rather than relying on a separate, global offset tag. This article explains the technical mechanics of how MKV stores, calculates, and applies timecode offsets to secondary audio tracks to ensure proper audio-video synchronization during playback.

The Segment and Cluster Timing Hierarchy

Matroska does not synchronize tracks using a static "track delay" metadata field in modern implementations. Instead, it relies on a hierarchical timing structure:

  1. Segment Info (TimestampScale): Defines the base unit of time for the entire file, defaulting to 1,000,000 nanoseconds (1 millisecond). All track timestamps are multiples of this scale.
  2. Cluster (Timestamp): Media data is divided into sequential containers called Clusters. Each Cluster contains a base Timestamp marking the absolute start time of that group of frames on the timeline.
  3. Block and SimpleBlock (Relative Timestamp): Individual audio frames are stored inside Block or SimpleBlock elements. Each block contains a 16-bit signed integer representing its timestamp relative to its parent Cluster's base timestamp.

Applying Positive Delays (Audio Starts After Video)

When a secondary audio track needs a positive delay (for example, starting +500ms after the video begins), the multiplexer adjusts the presentation timestamps (PTS) of that specific track's blocks.

  • The first audio packet of the misaligned track is assigned a PTS equal to the desired offset (e.g., 500ms).
  • The multiplexer places the first audio block into a Cluster whose base timestamp accommodates this offset, or sets the block's relative timestamp to match the target time.
  • The player reads the PTS of the audio block, compares it against the master video clock, and holds playback of that audio stream until the presentation time is reached.

Applying Negative Delays (Audio Starts Before Video)

When an audio track needs a negative offset (the audio needs to start earlier, or initial audio data must be skipped):

  • Timestamp Truncation and Pruning: Multiplexers typically discard all audio packets that fall entirely before timestamp 0.
  • Partial Frame Trimming (DiscardPadding): If an audio codec requires decoding to start before time zero (or mid-frame), the container uses the DiscardPadding element within a BlockGroup. This tells the decoder to process the audio frame for continuity but discard the specified number of nanoseconds from the start of the decoded output.
  • CodecDelay Element: For lossy codecs that have inherent encoder delay (such as Opus or AAC priming samples), the TrackEntry contains a CodecDelay value. The demuxer uses this value to shift timestamps backward so that the actual decoded audio aligns perfectly with the intended zero-mark.

The Role of Matroska Editions and Edit Lists

For complex timeline offsets or non-destructive editing, Matroska supports EditionEntry structures within its Chapter system:

  • An Edition can specify ChapterAtom elements with ChapterTimeStart and ChapterTimeEnd.
  • By defining a ordered chapter list, the container can map specific segments of an audio track to specific segments of the video timeline, effectively offsetting, looping, or re-ordering streams without modifying the underlying raw Block timestamps.

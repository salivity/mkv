How MKV Stores Custom Tags Without Breaking Playback

The Matroska (MKV) multimedia container uses a flexible, hierarchical binary structure that allows users to embed custom metadata and user-defined tags seamlessly. By relying on the Extensible Binary Meta Language (EBML) framework, MKV stores custom tags within dedicated, standardized metadata elements. This design ensures that playback engines can either interpret known properties or safely skip unknown custom fields without disrupting the decoding of the underlying audio and video streams.

The EBML Architecture and Element Skipping

MKV containers are built on EBML, which acts as a binary equivalent of XML. Every piece of data inside an MKV file is stored as an EBML element composed of three primary components:

  1. Element ID: A variable-length binary identifier defining the element type.
  2. Data Size: A descriptor indicating the exact length of the payload in bytes.
  3. Data Payload: The actual content of the element.

Because every element includes an explicit data size header, playback engines that encounter an unrecognized element ID simply read the size descriptor and skip forward that exact number of bytes. If a custom tag or an unsupported metadata structure is present, the parser bypasses it entirely rather than throwing a fatal parsing error.

Hierarchical Organization with the Tags Element

Matroska isolates all metadata within a top-level EBML element called Tags. This element is completely separated from the Tracks element (which defines codec settings) and the Cluster elements (which store the actual audio, video, and subtitle packets).

Inside the Tags master element, metadata is organized hierarchically:

  • Tag: A container that groups tags targeting a specific component of the file.
  • Targets: Defines the scope of the tag (such as the entire file, a specific video track, an audio stream, a chapter, or an attachment) using a standardized numeric TargetTypeValue.
  • SimpleTag: A nested key-value structure containing the actual metadata. It primarily consists of:
    • TagName: A UTF-8 string representing the name of the attribute (e.g., TITLE, ENCODER, or any custom user-defined string like INTERNAL_PROJECT_ID).
    • TagString: The UTF-8 text value for the corresponding key.
    • TagBinary: An optional field used to store arbitrary binary data payloads instead of text.
    • TagLanguage: Specifies the language of the tag value to support localization.

Because SimpleTag accepts arbitrary string values for TagName, users can define proprietary or custom keys without violating the Matroska specification.

Separation of Demuxing and Metadata Parsing

Media players divide the processing of an MKV file into two primary systems: the demuxer (which splits container data into raw packets for decoders) and the metadata reader.

Because metadata is stored outside the media Cluster payloads, custom tags have no impact on the interleaving, timecodes, or packet boundaries of media streams. When a playback engine initializes an MKV file, it queries the Tags element for standardized keys (such as TITLE, ARTIST, or COMMENT) to display in the user interface. Any custom key names that the player does not recognize are simply left unparsed in memory or ignored completely, allowing the demuxer to stream media packets to the decoders without interruption.

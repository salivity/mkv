How Avidemux Processes MKV in Stream Copy Mode

Stream-copying—commonly referred to as remuxing or direct stream copy—is a process where open-source tools like Avidemux alter, trim, or repackage a Matroska (MKV) file without re-encoding the underlying video and audio streams. This article explains the technical mechanics of how open-source transcoders parse MKV container structures, extract compressed elementary bitstreams, enforce keyframe boundaries, adjust presentation timestamps, and write the output file with zero quality loss and near-instant processing speeds.

1. Parsing and Demuxing the MKV Container

The MKV container is built on EBML (Extensible Binary Meta Language), a binary equivalent of XML. When Avidemux opens an MKV file for a stream-copy operation:

  • EBML Header and Segment Reading: The demuxer reads the file's EBML header to identify the Matroska version and parses the Segment element containing metadata, track definitions, and seek tables.
  • Track Identification: Avidemux parses the Tracks element to read the codec IDs (such as V_MPEG4/ISO/AVC for H.264 or A_AAC for AAC) and configuration records (such as AVC decoder configuration records/SPS/PPS data).
  • Extracting Elementary Streams: The demuxer separates individual data packets from the MKV Cluster elements, which hold SimpleBlock or BlockGroup structures containing raw compressed frames.

2. Bypassing the Codec Engine

In a standard transcoding pipeline, compressed packets pass through a decoder to become uncompressed raw YUV video and PCM audio frames, which are filtered and then re-encoded by an encoder.

During a stream-copy operation (Video Output: Copy and Audio Output: Copy in Avidemux), the entire decoding and encoding pipeline is bypassed. The raw compressed NAL units (for H.264/H.265) or audio frames pass directly from the demuxer buffer to the output muxer queue without mathematical transformation or generational loss.

3. Keyframe Navigation and Cut-Point Handling

Because video frames are inter-coded using temporal compression, Avidemux must enforce strict rules when trimming files in stream-copy mode:

  • Frame Types: Video streams contain Intra-coded frames (I-frames/IDR frames) that do not depend on other frames, and predicted frames (P-frames and B-frames) that rely on adjacent frames for reconstruction.
  • Cut Alignment: For stream copy to work cleanly without re-encoding, cut start points must occur precisely on an IDR/Keyframe. If a cut starts on a P-frame or B-frame, the decoder will lack the reference data, causing visual corruption (macroblocking or black screens).
  • Cue Table Parsing: Avidemux reads the MKV Cues element—an index mapping timestamps to byte offsets of keyframes—allowing the user to seek directly between I-frames.

4. Timestamp Calculation and Synchronization

When trimming or removing sections from an MKV file, raw stream copying requires recalculating the internal clock without altering packet payloads:

  • PTS and DTS Management: Every packet possesses a Presentation Timestamp (PTS, when the frame is displayed) and a Decoding Timestamp (DTS, when the frame is decoded). B-frames cause PTS and DTS to diverge due to frame reordering.
  • Offset Recalculation: Avidemux shifts the timestamps of remaining packets so the output file starts at timestamp zero (\(t = 0\)), preventing initial playback freezes.
  • Audio-Video Sync: Audio sample counts and video frame intervals are tracked to maintain synchronization across cut boundaries, dropping orphaned audio frames where necessary to align with the initial video keyframe.

5. Remuxing to the Destination Container

Once the requested stream segments are isolated and their timestamps recalculated, the output muxer writes the target file:

  • Writing Container Structures: A new EBML header, Track info segment, and metadata structure are written to the target file.
  • Packet Encapsulation: The raw elementary packets are packed into new MKV Cluster and Block elements.
  • Index Generation: Avidemux compiles a new Cues index and writes it along with the SeekHead element, ensuring the output file supports fast and accurate seeking in media players.

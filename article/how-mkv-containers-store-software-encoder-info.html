How MKV Containers Store Software Encoder Info

The Matroska (MKV) multimedia container stores custom software and encoder metadata within its header using a hierarchical binary format known as Extensible Binary Meta Language (EBML). By organizing data into distinct EBML master elements—specifically within the Segment Information and Tags sections—MKV files systematically record the software used to multiplex the file, the front-end application that wrote it, and granular custom encoder settings.

The EBML Header and Segment Information

Matroska files are structured like binary XML. At the root level, after the initial EBML header declaration, lies the Segment master element (0x18538067), which contains all file data and metadata. Inside the Segment element is the Info (Segment Information) element (0x1549A966), which acts as the general header for the entire presentation.

The Info block contains standard UTF-8 string elements specifically designated for software tracking:

  • MuxingApp (EBML ID 0x4D80): Identifies the underlying software or library used to assemble and multiplex the container (e.g., libmatroska, mkvmerge, or FFmpeg).
  • WritingApp (EBML ID 0x5741): Identifies the application, user interface, or higher-level tool used to generate the file (e.g., HandBrake, MakeMKV, or custom rendering engines).

These fields are structured as standard key-value pairs encoded in variable-length binary integers (VINTs) alongside their corresponding UTF-8 payload data.

Custom Encoder Settings and EBML Tags

While MuxingApp and WritingApp store top-level application names, custom encoder parameters (such as x264, x265, or AV1 encoding settings) are stored using Matroska’s Tags system (0x1254C367).

The Tags element contains one or more Tag structures, which further nest SimpleTag (0x67C8) elements containing:

  • TagName (0x45A3): The identifier for the metadata field, often set to strings like ENCODER or ENCODER_SETTINGS.
  • TagString (0x4487): The actual parameter string, which can hold extensive command-line flags, profile settings, rate-control methods, and preset definitions injected by the encoder.

These tags can be targeted globally to the entire segment or mapped to a specific track UID, ensuring that distinct video and audio tracks retain independent encoder metadata.

Track-Specific Codec Headers

In addition to general container tags, custom initialization data required by specific decoders or software encoders is stored inside the Tracks element (0x1654AE6B) under the CodecPrivate (0x63A2) field. While CodecPrivate primarily stores binary configuration records (such as AVC/H.264 SPS/PPS or HEVC parameter sets), some encoders insert custom identification headers directly into this binary field to ensure decoding libraries apply codec-specific optimizations.

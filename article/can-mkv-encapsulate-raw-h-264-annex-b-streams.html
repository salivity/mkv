Can MKV Encapsulate Raw H.264 Annex B Streams?

This article explores whether the Matroska (MKV) container can directly encapsulate raw H.264 Annex B byte streams without modification. While raw H.264 streams rely on start codes to separate Network Abstraction Layer (NAL) units, the standard Matroska specification requires the AVCC format, which uses length-prefixed NAL units and extracts parameter sets into container headers. Consequently, standard MKV muxers must convert Annex B streams during encapsulation rather than storing them in their raw, native format.

Understanding H.264 Annex B vs. AVCC

H.264 video data exists in two primary encapsulation formats:

  • Annex B (Byte Stream Format): Commonly used in live broadcasting (such as MPEG-TS) and raw elementary video files (.h264 or .264). It separates NAL units using 3-byte or 4-byte start codes (0x000001 or 0x00000001). Sequence Parameter Sets (SPS) and Picture Parameter Sets (PPS) are transmitted periodically in-band alongside the video frames.
  • AVCC (Length-Prefixed Format): Defined in ISO/IEC 14496-15 and standard in file-based containers like MP4 and MKV. It replaces start codes with a fixed-length prefix (usually 4 bytes) indicating the size of each NAL unit. The SPS and PPS are removed from the video stream and stored globally in the container's track header.

The Matroska Standard: V_MPEG4/ISO/AVC

Under the official Matroska specification, standard H.264 tracks use the CodecID V_MPEG4/ISO/AVC.

This implementation explicitly mandates the AVCC format. An MKV container cannot store raw Annex B start codes under standard specifications. When muxing an Annex B stream:

  1. Header Generation: The muxer parses the initial SPS and PPS NAL units from the Annex B stream and packages them into the Matroska CodecPrivate element as an AVCDecoderConfigurationRecord.
  2. Stream Conversion: The muxer strips all 0x000001 or 0x00000001 start codes from the video payload and replaces them with NAL unit length indicators.

Legacy VFW Compatibility Mode

Historically, Matroska introduced a fallback mode using the CodecID V_MS/VFW/FOURCC (Video for Windows). In this mode, raw video frames could theoretically be stored using a FourCC code like H264 or X264 with Annex B start codes intact.

However, this mode is deprecated, violates modern Matroska best practices, and causes playback or seeking failures across modern media players and hardware decoders.

Summary

An MKV container cannot store raw H.264 Annex B byte streams directly under valid, modern specifications. Muxing tools such as FFmpeg, MKVToolNix, and GStreamer will automatically transform the Annex B stream into the AVCC format during the encapsulation process to ensure standard compliance and compatibility.

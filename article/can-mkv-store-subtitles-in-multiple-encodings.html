Can MKV Store Subtitles in Multiple Encodings?

This article examines how the Matroska (MKV) container handles embedded text subtitles across multiple tracks and whether distinct character encodings can coexist within a single file. While an MKV file can store an unlimited number of subtitle tracks representing different languages and writing systems, the official Matroska container specification requires all standard text-based subtitles to be encoded in UTF-8, preventing the coexistence of disparate legacy character encodings in playable text streams.

The Matroska Specification and UTF-8 Requirement

The Matroska multimedia container format relies on the Extensible Binary Meta Language (EBML). Under the official specification, all text-based subtitle formats (such as SubRip S_TEXT/UTF8 and Advanced SubStation Alpha S_TEXT/ASS) must be stored using UTF-8 encoding.

Because UTF-8 is a universal character encoding capable of encoding every valid code point in Unicode, there is no technical necessity within the container to support competing legacy character encodings (such as ISO-8859-1, Windows-1252, Shift-JIS, or GB2312).

How Muxers Handle Multiple Source Encodings

When creating an MKV file using standard muxing tools like mkvmerge (part of MKVToolNix) or FFmpeg, the software processes input subtitle files that may originate in various distinct encodings:

  1. Source Detection: The user or muxing tool specifies or detects the character set of each input subtitle file (for example, Track 1 in Windows-1256 for Arabic, and Track 2 in Shift-JIS for Japanese).
  2. Transcoding to UTF-8: During the multiplexing process, the muxer decodes each source file from its native character set and transcodes the text into standardized UTF-8.
  3. Storage: The final MKV file stores both subtitle tracks as individual streams, but both are encoded strictly in UTF-8.

As a result, while the original source files may have had distinct encodings, the embedded text subtitle tracks within the resulting MKV file do not retain those separate encodings.

Supporting Diverse Scripts Simultaneously

Although an MKV file cannot store standard text subtitle streams in varying legacy encodings, it fully supports multiple tracks displaying completely different alphabets and scripts simultaneously.

Because UTF-8 encompasses global character sets, an MKV container can store:

  • Track 1: English (Latin script)
  • Track 2: Greek (Greek script)
  • Track 3: Russian (Cyrillic script)
  • Track 4: Chinese (Simplified/Traditional Hanzi)

All tracks exist side-by-side in harmony, unified under the UTF-8 standard, ensuring consistent rendering across modern media players without character corruption (mojibake).

Non-Text and Attachment Exceptions

  • Bitmap Subtitles: Image-based subtitle tracks, such as DVD VobSub (S_VOBSUB) or Blu-ray PGS (S_HDMV/PGS), store graphical representations of text rather than character-encoded strings. These tracks do not use character encodings at all.
  • File Attachments: MKV allows arbitrary files to be embedded as attachments. If subtitle files are attached as raw binary payloads rather than multiplexed as active subtitle tracks, they can retain their original, distinct legacy character encodings, though media players will not display them automatically as switchable subtitles during playback.

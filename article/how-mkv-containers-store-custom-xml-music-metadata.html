How MKV Containers Store Custom XML Music Metadata

The Matroska (MKV/MKA) multimedia container format stores rich, custom music metadata through a standardized, hierarchical tagging system built into its core Extensible Binary Meta Language (EBML) architecture. By converting structured XML documents into native EBML tag elements, Matroska allows users and developers to attach comprehensive track-level audio details—such as artist credits, track numbers, replay gain values, and synchronized lyrics—directly to individual streams within the file.

The EBML Tagging System Architecture

Matroska does not simply append a raw XML text file to the container. Instead, it parses custom XML metadata into binary EBML elements within a dedicated top-level Tags master element.

The Tags element contains one or more Tag elements, each consisting of two primary components:

  1. Targets: Defines what the metadata applies to (the whole file, a specific track, a chapter, or an attachment).
  2. SimpleTag: Contains the actual key-value pairs representing the metadata fields.

Target Mapping and Track Association

To associate custom metadata with a specific music track rather than the entire media container, Matroska uses the Targets element.

  • TrackUID: Specifies the unique ID of the specific audio track the metadata belongs to.
  • TargetTypeValue: Defines the logical level of the target in a standard Matroska hierarchy (e.g., 50 for Album, 30 for Track/Song, 10 for Movement or Part).

This structure ensures that multiple audio tracks within a single MKV file can carry completely independent metadata profiles.

The Structure of SimpleTag Elements

Metadata keys and values are defined using nested SimpleTag structures. Each SimpleTag contains:

  • TagName: The identifier for the metadata field (e.g., ARTIST, TITLE, ISRC, BPM).
  • TagString: The text value of the tag stored in UTF-8 encoding.
  • TagBinary: An optional binary payload, useful for raw data payloads.
  • TagLanguage: An ISO 639-2 language code indicating the language of the tag value.
  • TagDefault: A boolean flag indicating if this tag is the default choice for the given language.

SimpleTag elements can also be nested within other SimpleTag elements to create multi-level metadata, such as detailed performer roles (e.g., mapping an ARTIST tag with a nested INSTRUMENT tag).

Example XML Representation

Before being multiplexed into EBML, metadata is typically written in an XML structure matching the Matroska specification:

<Tags>
  <Tag>
    <Targets>
      <TargetTypeValue>30</TargetTypeValue>
      <TrackUID>1234567890</TrackUID>
    </Targets>
    <SimpleTag>
      <TagName>TITLE</TagName>
      <TagString>Track Title</TagString>
    </SimpleTag>
    <SimpleTag>
      <TagName>ARTIST</TagName>
      <TagString>Lead Performer</TagString>
    </SimpleTag>
    <SimpleTag>
      <TagName>CUSTOM_DATABASE_ID</TagName>
      <TagString>XYZ-98765</TagString>
    </SimpleTag>
  </Tag>
</Tags>

Custom Tag Extensibility

Matroska maintains a list of officially recognized tag names, but the container format is non-restrictive. Any custom TagName defined in the XML input is preserved and converted to EBML during multiplexing. Tools like mkvmerge or mkvpropedit parse the XML file, validate the hierarchy against the Matroska specifications, and write the structured data directly into the MKV container's Tags block without requiring re-encoding of the audio streams.

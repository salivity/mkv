Maximum Cluster Payload Size in MKV Explained

In a Matroska (MKV) container, the maximum payload size of a single Cluster element is determined by a combination of the Extensible Binary Meta Language (EBML) data architecture, relative block timestamp limitations, and muxer splitting parameters. While the structural format theoretically allows for petabyte-scale Clusters, practical file creation enforces much smaller payload limits to ensure seeking performance, memory stability, and adherence to video keyframe intervals.

1. EBML Variable-Size Integer (VINT) Limit

At the binary level, an MKV Cluster is an EBML element. The size of an EBML element's payload is declared using a Variable-Size Integer (VINT):

  • Standard VINT Length: An EBML size descriptor can be up to 8 bytes long. An 8-byte VINT allows a maximum theoretical addressable payload size of \(2^{56} - 2\) bytes (over 72 petabytes).
  • Unknown Size Flag: EBML also supports an "unknown" or undefined data size (a VINT filled with all 1s). This allows a Cluster to have an open-ended payload size, commonly used in live streaming scenarios where the total payload is not known in advance.

2. Relative Timestamp Limitations (16-bit Integer)

A Cluster contains a base Timestamp element, while the child elements inside it (SimpleBlock or BlockGroup) define their timing relative to this base value.

  • 16-bit Signed Offset: The relative timestamp inside each Block is stored as a signed 16-bit integer (int16), which ranges from -32,768 to +32,767.
  • TimestampScale Dependency: By default, the MKV TimestampScale is set to 1,000,000 nanoseconds (1 millisecond per unit). This restricts the duration span of media within a single Cluster to roughly ±32.7 seconds. Consequently, the payload size is capped by how much audio, video, and subtitle data can exist within that 32-second time window.

3. Keyframe Intervals and GOP Structure

Clusters typically serve as random-access points for media playback. For efficient decoding and seeking:

  • Muxers start a new Cluster at every video keyframe (IDR/I-frame).
  • The size of the Group of Pictures (GOP) directly dictates the payload size. Higher video bitrates combined with longer intervals between keyframes yield larger Cluster payloads.

4. Muxer Splitting Configurations

Software muxers (such as mkvmerge or libavformat) enforce internal parameters that override theoretical maximums to maintain optimal playback:

  • Maximum Duration per Cluster: Most muxers limit a Cluster's duration to between 1,000 ms and 5,000 ms by default.
  • Maximum Data Size Limits: Muxers often implement a hard payload threshold (e.g., splitting a Cluster if it exceeds a specific byte limit, such as 5 MB to 30 MB) to prevent buffer overflows in hardware decoders.
  • Cue Indexing Strategy: Clusters must align with the container’s CueTrack entries for seeking; excessively large Cluster payloads degrade seeking precision and increase indexing overhead.

How MKV Stores Field Order for Video Deinterlacing

The Matroska (MKV) multimedia container uses standardized metadata elements within its track headers to define the scanning format and field order of interlaced video streams. By setting specific Extensible Binary Meta Language (EBML) elements—primarily FlagInterlaced and FieldOrder—the container explicitly communicates whether a video is progressive or interlaced, and whether the top or bottom field takes temporal precedence. This container-level signaling ensures that video splitters, decoders, and playback renderers invoke the correct deinterlacing algorithms to eliminate combing artifacts and motion judder.

Matroska EBML Structure for Video Tracks

Matroska organizes data using a hierarchical EBML system. Video stream properties are defined inside the TrackEntry master element under the Video sub-element. When an MKV contains interlaced content, two primary EBML tags dictate how the fields must be interpreted:

  1. FlagInterlaced (Element ID: 0x9A): Defines whether the video stream is interlaced.
    • 0: Unspecified
    • 1: Interlaced
    • 2: Progressive
  2. FieldOrder (Element ID: 0x9D): Specifies the field dominance and display order.

FieldOrder Values and Definitions

The FieldOrder element provides direct instructions regarding the temporal and spatial layout of video lines:

  • Value 0 (Progressive): The frame contains no separate fields; all lines are captured at the same point in time.
  • Value 1 (Top Field First - TFF): The top field (even-numbered scanlines) represents an earlier point in time than the bottom field (odd-numbered scanlines) and must be displayed or processed first.
  • Value 2 (Undetermined): The video is interlaced, but the field dominance is unknown.
  • Value 6 (Bottom Field First - BFF): The bottom field represents an earlier point in time and must be displayed or processed first.
  • Value 9 (BFF with Fields Swapped): The spatial layout is inverted, requiring custom mapping during display.
  • Value 14 (TFF with Fields Swapped): The spatial layout is inverted, requiring custom mapping during display.

Container Metadata vs. Bitstream Flags

Interlaced video formats, such as MPEG-2, H.264 (AVC), and H.265 (HEVC), often contain their own field order signaling inside the elementary bitstream (such as Sequence Parameter Sets or Picture Timing SEI messages). However, relying solely on codec-level bitstream parsing can cause latency or playback errors if the headers are missing, malformed, or misread by a demuxer.

The MKV container provides a standardized, codec-agnostic layer. When a container parser loads the MKV file, it reads the TrackEntry header before decoding video packets, passing the correct field order directly to the playback pipeline.

Playback and Deinterlacing Pipeline

When playing an MKV file, the deinterlacing workflow follows these steps:

  1. Demuxing: The MKV splitter (such as FFmpeg's libavformat or LAV Splitter) parses the TrackEntry EBML elements.
  2. Media Type Negotiation: The splitter flags the media format downstream with properties such as TFF or BFF.
  3. Deinterlacer Activation: If hardware acceleration (DXVA, D3D11VA, VAAPI) or software filters (Yadif, Bボブ, Westley) are enabled, the video engine uses the field order tag to sequence the fields chronologically.
  4. Frame Reconstruction: The deinterlacer interpolates or weaves the alternating fields into full progressive frames (e.g., converting 1080i 59.94 fields per second into 1080p 59.94 frames per second) matching the correct temporal motion.

If the FieldOrder tag matches the underlying video data, the player renders smooth motion. If the tag is incorrect or inverted, the player reconstructs fields in reverse chronological sequence, resulting in noticeable back-and-forth motion stutter on moving objects.

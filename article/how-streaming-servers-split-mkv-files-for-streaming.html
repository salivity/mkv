How Streaming Servers Split MKV Files for Streaming

Streaming servers process monolithic MKV (Matroska) files for progressive download and adaptive streaming by demuxing the underlying media tracks, identifying keyframe boundaries, and repackaging the audio and video into small, sequential segments. Because native MKV files are not universally supported for direct segment-based web delivery, servers typically transmux the content on the fly into fragmented formats—such as fragmented MP4 (fMP4) or MPEG-TS—and deliver them via protocols like HLS and MPEG-DASH.

1. Parsing the MKV Container (EBML and Clusters)

An MKV file is built on the Extensible Binary Meta Language (EBML). Media data inside an MKV file is organized into structural units called Clusters, which contain a sequence of simple blocks (audio and video frames) with relative timestamps:

  • EBML Header & Segment Info: Provides global metadata, including codec types, resolution, and track identifiers.
  • SeekHead & Cues: Acts as the index table, mapping specific presentation timestamps to their physical byte offsets within the file.
  • Clusters: The actual media payload grouped into manageable time blocks.

The streaming server first reads the Cues element to map out the exact byte locations of keyframes (I-frames or IDR frames).

2. Keyframe Detection and Segmentation

Progressive fragmented delivery requires that every media segment begins with an independent keyframe, allowing a media player to decode the fragment without needing data from preceding segments.

  • GOP (Group of Pictures) Analysis: The server analyzes the GOP structure from the video track.
  • Split Points: Segment boundaries are determined based on keyframe intervals (typically every 2 to 6 seconds). The server ensures that segment cuts align strictly with IDR frames so video playback starts smoothly at any chunk boundary.

3. On-the-Fly Transmuxing (Remuxing)

Most modern client players (such as HTML5 video players using MSE) do not natively decode fragmented MKV streams. To solve this, streaming engines transmux the file in memory without re-encoding:

  1. Demuxing: The server extracts the raw elementary streams (e.g., H.264/H.265 video, AAC/Opus audio) from the MKV container.
  2. Repackaging into fMP4/TS: The server encapsulates the raw media frames into fragmented MP4 containers (moof and mdat atom pairs) or MPEG-TS packets.
  3. Audio-Video Synchronization: Timestamps (PTS and DTS) extracted from the MKV clusters are rewritten into the new segment headers to maintain continuous lip-sync.

4. Manifest Generation and Progressive Delivery

Once split points are calculated and fragments are formatted, the server makes the media accessible through standard HTTP web protocols:

  • Manifest Files: The server generates dynamic index files (such as an .m3u8 playlist for HLS or an .mpd manifest for MPEG-DASH). These files list the URLs or byte-ranges for each progressive chunk.
  • Byte-Range Requests: Instead of physically splitting the original MKV file into thousands of individual files on disk, modern streaming origin servers (like NGINX with VOD modules, Wowza, or Nimble) keep the master MKV intact. When a client requests segment #5, the server reads the corresponding byte range from the MKV, converts that slice into an fMP4 fragment in RAM, and sends it as an HTTP response.
  • Progressive Buffering: The client receives these consecutive chunks over standard HTTP/HTTPS GET requests, appending them into the browser's source buffer for seamless, uninterrupted playback.

Preserving Original Timecodes When Remuxing MKV

Remuxing an MKV file to another container format, such as MP4 or TS, transfers audio, video, and subtitle streams without re-encoding the underlying compressed data. To ensure that playback remains synchronized and frame-accurate, video converters extract and translate the original packet-level timestamps from the Matroska container and write them directly into the timing structures of the target container. This article explains the exact mechanisms converters use to preserve presentation timestamps, decode timestamps, and variable frame rates during the remuxing process.

Extraction of Elementary Stream Packets

Matroska (.mkv) stores compressed data in SimpleBlock or BlockGroup elements. Each block contains an elementary stream packet (such as an H.264, H.265, or AAC frame) accompanied by relative timestamp metadata.

When a converter remuxes a file, it bypasses the video and audio decoders. Instead, a demuxer reads the raw compressed packets along with two critical timing values attached to each frame:

  • Presentation Timestamp (PTS): Determines the exact time a frame must be displayed on the screen.
  • Decoding Timestamp (DTS): Dictates the order and timing in which compressed frames must be decoded by the hardware or software player (essential for streams with B-frames).

Timebase Rescaling and Clock Conversion

Different container formats measure time using different internal clocks (timebases).

  • In Matroska, time is typically measured in nanoseconds, with a default TimestampScale setting clock ticks to 1 millisecond (1 kHz).
  • In MP4 containers, each track often defines its own timescale (e.g., 90,000 Hz for video or the audio sample rate like 48,000 Hz for audio).

To prevent synchronization drift, the converter mathematically rescales each packet’s PTS and DTS to match the target container's timebase:

\[\text{New Timestamp} = \text{round}\left(\text{Original Timestamp} \times \frac{\text{Target Timescale}}{\text{Source Timescale}}\right)\]

Because this is a linear mathematical conversion of integer ticks, the absolute temporal position of every single frame is precisely maintained down to sub-millisecond accuracy.

Handling Variable Frame Rates (VFR)

MKV natively supports Variable Frame Rates (VFR) by explicitly storing a unique timestamp for every individual frame rather than enforcing a fixed interval.

When remuxing VFR MKV files to containers like MP4:

  1. The converter preserves the individual time offsets per frame.
  2. It writes these intervals into the container's timing atom (such as the stts or Time-to-Sample atom in MP4).
  3. The player reads the table of varying durations to render each frame at its intended original duration, preventing fast-forward or slow-motion artifacts.

Synchronizing Start Offsets and Edit Lists

Source MKV files may contain audio or video tracks with non-zero start times, track delays, or internal cut points defined by Matroska Chapter or Edition elements.

During remuxing, converters manage these offsets by:

  • Normalizing Initial Timestamps: Shifting the lowest DTS to zero across all tracks so playback starts cleanly without negative timestamps.
  • Writing Container-Specific Edit Lists: Using metadata structures like the edts/elst (Edit List) atom in MP4 to instruct players to delay or trim specific tracks, maintaining the original relative audio-to-video alignment without re-encoding the media streams.

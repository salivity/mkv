Can MKV Store UTF-8, UTF-16, and ASCII Subtitles?

The Matroska (MKV) container natively supports text subtitle tracks encoded in UTF-8 and standard ASCII, but it does not support raw UTF-16 for standard subtitle streams. While ASCII works seamlessly because it is a direct subset of UTF-8, the Matroska specification strictly mandates UTF-8 encoding for all text-based subtitles. Consequently, any subtitles originally formatted in UTF-16 must be converted to UTF-8 before or during the process of muxing them into an MKV file.

UTF-8: The Matroska Standard

The Matroska specification requires all text-based subtitle formats—such as SubRip (SRT), SubStation Alpha (SSA/ASS), and WebVTT—to use UTF-8 character encoding. UTF-8 provides universal compatibility across multiple languages and alphabets while maintaining efficient file sizes. When players read text subtitle tracks from an MKV container, they parse the data expecting UTF-8.

ASCII Compatibility

Standard 7-bit ASCII text is fully compatible with the MKV format. Because UTF-8 is designed to be backward-compatible with ASCII, the first 128 characters of UTF-8 are identical to standard ASCII byte-for-byte. As a result, any pure ASCII subtitle file is already valid UTF-8 and can be stored directly within an MKV track without modification or loss of data.

UTF-16 Handling

MKV cannot store text subtitle tracks in UTF-16 directly. If you attempt to mux a UTF-16 encoded subtitle file using standard tools like MKVToolNix or FFmpeg, the software will automatically detect the encoding and transcode the text into UTF-8 before embedding it into the container.

If raw UTF-16 bytes were forced into a text subtitle track without conversion, media players would fail to render the subtitles properly, resulting in garbled text (mojibake) or playback errors. The only way to store a UTF-16 file in its original format inside an MKV without conversion is as a general file attachment, but attachments cannot be rendered on-screen as synchronized subtitle tracks by media players.

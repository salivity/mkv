How MKV Stores ContentEncAlgo Encryption Data

The Matroska (MKV) multimedia container format utilizes an extensible Extensible Binary Meta Language (EBML) structure to handle protected and encrypted media streams. Within this architecture, encryption metadata is organized in the track headers under specific structural elements. The container specifies the cipher used via the ContentEncAlgo element, alongside corresponding key identifiers and cipher configurations, allowing demuxers and cryptographic modules to identify, extract, and decrypt media blocks before decoding.

The EBML Structural Hierarchy

MKV organizes encryption parameters inside the metadata header of each individual media track. Encryption is treated as a sub-type of content encoding (which also covers compression). The hierarchy is structured as follows:

  • Segment (0x18538067): The top-level root container for all MKV metadata and data.
    • Tracks (0x1654AE6B): Contains information about all streams in the file.
      • TrackEntry (0xAE): Describes an individual video, audio, or subtitle track.
        • ContentEncodings (0x6D80): Wraps one or more encoding configurations.
          • ContentEncoding (0x6264): Defines a specific encoding step and its order.
            • ContentEncodingType (0x5031): Set to 1 to indicate encryption (as opposed to 0 for compression).
            • ContentEncryption (0x5035): The parent container for all cryptographic settings.

The Role of ContentEncAlgo

Inside the ContentEncryption element, the ContentEncAlgo (0x47E1) tag is stored as an unsigned integer (unsigned int). It explicitly tells the playback engine which cryptographic algorithm was used to encrypt the track's raw payload data.

The Matroska specification maps the integer values of ContentEncAlgo to specific algorithms:

  • 0 - Not Encrypted: The data remains in plain text (often used as a passthrough or default).
  • 1 - DES: Data Encryption Standard.
  • 2 - 3DES: Triple Data Encryption Standard (Triple-DES).
  • 3 - Twofish: Twofish symmetric key block cipher.
  • 4 - Blowfish: Blowfish symmetric block cipher.
  • 5 - AES: Advanced Encryption Standard (Rijndael).

Complementary Encryption Metadata Elements

ContentEncAlgo does not work in isolation; it works in tandem with several sibling EBML elements located within ContentEncryption to fully define the cryptographic profile:

  • ContentEncKeyID (0x47E2): A binary payload containing the Key Identifier (Key ID). The demuxer uses this ID to query a digital rights management (DRM) system or key repository for the correct decryption key without exposing the key itself inside the container.
  • ContentEncAESSettings (0x47E7): If ContentEncAlgo is set to 5 (AES), this sub-element defines AES-specific behavior.
    • AESSettingsCipherMode (0x47E8): An unsigned integer defining the block cipher mode. For instance, value 1 represents AES-CTR (Counter Mode), commonly used in modern media streaming, while value 2 represents AES-CBC.

Payload Storage and Decryption Flow

When an MKV file containing encrypted media is demuxed:

  1. Header Parsing: The parser traverses the TrackEntry and encounters ContentEncodings. If ContentEncodingType is 1, it reads the ContentEncryption block.
  2. Algorithm Identification: The parser reads ContentEncAlgo to configure the correct decryption module (e.g., AES-128 or AES-256).
  3. Key Retrieval: The parser extracts the binary data from ContentEncKeyID and requests the matching secret key from the cryptographic provider or DRM client.
  4. Frame Processing: Media frames are stored inside Cluster elements as SimpleBlock or BlockGroup structures. When encrypted, the payloads of these blocks contain ciphertext. The playback system routes this ciphertext through the initialized cipher engine using the designated ContentEncAlgo specifications.
  5. Passing to Decoder: Once decrypted, the raw elementary stream data (e.g., H.264, HEVC, AAC) is forwarded to the designated media decoder for rendering.

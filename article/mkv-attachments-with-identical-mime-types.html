MKV Attachments with Identical MIME Types

The Matroska (MKV) multimedia container format natively supports embedding arbitrary binary attachments, such as subtitle fonts, cover images, and documentation. When an MKV container holds multiple attachments sharing the exact same MIME type, it prevents conflicts and ensures accurate file retrieval by utilizing distinct metadata fields, individual file names, and unique numerical identifiers (FileUID) defined in its Extensible Binary Meta Language (EBML) structure.

The EBML Attachment Structure

Matroska organizes attached data within the top-level Attachments element, which contains one or more AttachedFile master elements. Instead of indexing files strictly by their MIME type (FileMediaType), the specification treats the MIME type merely as a content descriptor.

Each AttachedFile entry contains distinct child elements:

  • FileUID: A unique 64-bit unsigned integer that serves as an immutable identifier for each specific file inside the container.
  • FileName: The UTF-8 string representation of the original filename, including its file extension (e.g., font_regular.ttf and font_bold.ttf).
  • FileMediaType: The MIME type string (e.g., font/sfnt or image/jpeg), which can be repeated across any number of attachments.
  • FileDescription: An optional text string providing context or details regarding the specific attachment.
  • FileData: The raw binary data of the embedded file.

How Parsers and Players Differentiate Identical MIME Types

Media demuxers and playback engines do not encounter ambiguity when reading attachments with duplicate MIME types because they reference the structural metadata rather than relying solely on the MIME definition:

  1. Filename Resolution: When rendering advanced subtitles (such as SSA/ASS), the subtitle engine requests embedded fonts by their declared font names or file names. Even if twenty attached fonts share the font/ttf or application/x-font-truetype MIME type, the demuxer matches the subtitle engine's request against the FileName element of each attachment.
  2. Cover Art Selection: For media players displaying embedded cover art, files sharing the image/jpeg or image/png MIME types are prioritized using standardized naming conventions within the FileName field (such as cover.jpg, small_cover.jpg, or cover_land.jpg) or dedicated Matroska tag elements targeting specific FileUID values.
  3. Sequential and UID Fallbacks: If two attachments possess both identical MIME types and identical filenames, the demuxer uses the unique FileUID to separate the assets in memory, typically exposing them to downstream filters in the order they appear in the EBML stream.

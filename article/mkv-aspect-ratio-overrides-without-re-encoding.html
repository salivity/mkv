MKV Aspect Ratio Overrides Without Re-encoding

Matroska (MKV) containers manage custom aspect ratio overrides by altering metadata headers embedded in the container format rather than modifying the underlying video stream. By utilizing standardized Extensible Binary Meta Language (EBML) track properties—specifically DisplayWidth and DisplayHeight—the MKV container instructs media players to stretch, squeeze, or crop the decoded video frames during rendering. This container-level signaling completely bypasses the need for re-encoding, preserving 100% of the original video quality and executing instantly.

The Separation of Container and Bitstream

To understand how MKV overrides aspect ratios, it is essential to distinguish between the coded frame data and the playback instructions:

  • Storage Aspect Ratio (SAR): The physical resolution of the stored video frames (e.g., 720×480 pixels).
  • Display Aspect Ratio (DAR): The intended geometric ratio visible to the viewer on screen (e.g., 16:9 or 4:3).
  • Pixel Aspect Ratio (PAR): The shape of individual pixels (non-square vs. square).

In an encoded bitstream (such as H.264/AVC or H.265/HEVC), aspect ratio information is often embedded within the Sequence Parameter Set (SPS) or Video Usability Information (VUI). However, an MKV container wraps around this bitstream, acting as an administrative layer. When an aspect ratio override is applied, the container alters its own track header parameters, instructing the media player's demuxer to set the presentation dimensions regardless of what the internal bitstream headers declare.

Key EBML Track Elements in Matroska

The Matroska specification utilizes a set of hierarchical elements under the TrackEntry -> Video structure to define display geometry:

  1. PixelWidth and PixelHeight: These integers define the actual physical dimensions of the encoded video frames as stored in the file.
  2. DisplayWidth and DisplayHeight: These integers define the target resolution at which the video should be rendered on a display. For example, a 720×480 (3:2 storage) video can have its DisplayWidth set to 854 and DisplayHeight set to 480 to force a 16:9 presentation.
  3. DisplayUnit: This element defines how DisplayWidth and DisplayHeight should be interpreted (e.g., pixels, centimeters, inches, or display aspect ratio). The default value is 0 (pixels).
  4. PixelCropBottom, PixelCropTop, PixelCropLeft, PixelCropRight: These elements specify pixels that should be removed from the decoded picture edges before scaling to the display dimensions.

How the Playback Pipeline Executes the Override

When a media player opens an MKV file, the rendering pipeline executes the override through the following stages:

  1. Demuxing: The demuxer reads the MKV EBML header and extracts the TrackEntry information for the video stream.
  2. Flag Prioritization: Modern media players (such as VLC, MPV, or DirectShow/Media Foundation filters) are programmed to give container-level metadata precedence over stream-level metadata.
  3. Decoding: The video decoder processes the raw bitstream and outputs uncompressed video frames at the native PixelWidth and PixelHeight.
  4. Renderer Scaling: Before outputting to the screen, the video renderer queries the demuxer for display properties. It detects the DisplayWidth and DisplayHeight values, calculates the target DAR, and scales the output frame using hardware-accelerated bilinear, bicubic, or Lanczos scaling algorithms.

Editing Metadata with Tools like mkvpropedit

Because aspect ratio parameters reside exclusively in the EBML header at the beginning of the file (and occasionally in a secondary header block), tools such as mkvpropedit (part of the MKVToolNix suite) can modify the aspect ratio in milliseconds. The tool opens the file in read-write mode, locates the specific EBML IDs for DisplayWidth and DisplayHeight, rewrites the integer values, and closes the file without reading, decoding, or rewriting any of the compressed video packets.

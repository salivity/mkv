How MKV Stores Closed Caption Timecode Offsets

The Matroska (MKV) container manages timecode offsets for embedded closed captions and subtitles through a hierarchical, timestamp-based architecture defined by Extensible Binary Meta Language (EBML). Instead of relying on a single absolute timestamp per caption event, MKV calculates presentation timing dynamically using global scaling parameters, cluster-level reference timestamps, block-level relative offsets, and track-level timing modifiers to maintain frame-accurate synchronization with audio and video streams.

The Segment TimestampScale

At the root level of an MKV file, the Segment Information element defines a global parameter called TimestampScale (formerly TimecodeScale). This value defines the base time resolution for the entire file in nanoseconds, with the default setting typically being 1,000,000 nanoseconds (representing a 1-millisecond resolution). Every subsequent timestamp offset in the file is multiplied by this scaling factor to determine real-world presentation time.

Cluster Base Timestamps

Data within an MKV container is partitioned into sequential containers known as Clusters. Each cluster represents a specific time range of the presentation and contains a mandatory Timestamp element. This element sets the absolute base presentation time for all media samples—including video frames, audio packets, and closed caption entries—stored within that specific cluster.

Block-Level Relative Timecode Offsets

Closed caption data is packaged inside clusters using either SimpleBlock or BlockGroup elements:

  • Relative Timecodes: Inside each block header, the MKV specification stores a 16-bit signed integer representing the block's time offset relative to the parent Cluster’s base Timestamp.
  • Final Presentation Timestamp (PTS): The exact display time of a caption is calculated as:
    PTS = (Cluster Timestamp + Block Relative Offset) × TimestampScale
  • BlockDuration: While SimpleBlock is common for video and audio, subtitle and caption tracks frequently use BlockGroup elements because they support a child element named BlockDuration. This explicitly defines how long a caption remains visible before disappearing. If BlockDuration is omitted, the caption remains on screen until the next caption block arrives or the stream dictates an explicit clear command.

Track-Level Timecode Modifiers

MKV allows track-specific timing adjustments within the Track headers:

  • TrackTimestampScale: A track can define a custom scaling multiplier to handle subtitle streams that run on a non-standard clock without altering the global segment scale.
  • CodecDelay / SeekPreRoll: For certain formats requiring decoder lead-in time, codec delay elements shift timestamps forward or backward to guarantee synchronization upon random seek operations.

Discrete Subtitle Tracks vs. Embedded Bitstream Captions

The mechanism for storing timecode offsets varies depending on whether closed captions are stored as dedicated subtitle tracks or multiplexed within the video bitstream:

  • Discrete Caption Tracks (SRT, ASS/SSA, VobSub): Text-based caption files have their source timestamps converted during multiplexing. The container strips or normalizes the internal text timecodes and assigns each line to an MKV BlockGroup with corresponding relative offsets and durations.
  • Bitstream-Embedded Closed Captions (CEA-608 / CEA-708): Closed caption data embedded directly into video NAL units (such as SEI user data in H.264 or H.265) relies on the video frame's own block timestamp. In this scenario, the MKV container stores the timecode offset for the video frame, and the embedded caption decoder derives its synchronization directly from the underlying video Presentation Timestamp.

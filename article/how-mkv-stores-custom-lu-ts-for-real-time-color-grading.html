How MKV Stores Custom LUTs for Real-Time Color Grading

The Matroska (MKV) container format stores custom Look-Up Tables (LUTs) primarily through its extensible binary attachment subsystem and dedicated metadata tagging structure, enabling non-destructive, real-time color transformation during playback. This article examines the internal architecture of MKV container specifications, the method for embedding 1D and 3D LUT data files, and how video rendering pipelines extract and apply these tables dynamically on the GPU.

The Matroska EBML Architecture and Attachments

Matroska is built on Extensible Binary Meta Language (EBML), a hierarchical binary format analogous to XML. This architecture allows MKV to encapsulate arbitrary binary assets alongside traditional audio and video elementary streams without requiring separate sidecar files.

To store a LUT (such as a .cube, .3dl, or .lut file), the container utilizes the standard <Attachments> element (EBML ID 0x1941A469). Within this master element, one or more <AttachedFile> entries are created with specific sub-elements:

  • FileName (0x466E): Stores the name of the LUT file (e.g., creative_grade.cube).
  • FileMediaType (0x4660): Defines the MIME type, typically set to an application-specific or generic type like application/x-lut or text/plain.
  • FileData (0x465C): Contains the raw binary or plaintext data of the Look-Up Table.
  • FileUID (0x46AE): A unique 64-bit integer used to reference the specific attachment across other parts of the container.

Linking LUTs to Video Streams via Tags

Embedding the file is only the first step; the container must also signal to the demuxer which video stream the LUT should be applied to. This is handled through the <Tags> element (EBML ID 0x1254C367).

A tag targets the specific video track using the <TargetTypeValue> and <TrackUID>. Inside the <SimpleTag> structure, a metadata field (such as LUT_ATTACHMENT_UID or a custom processing directive) points directly to the FileUID of the attached LUT. This enables multi-track or multi-version MKV files to map distinct color profiles to specific video streams without altering the underlying encoded video frames.

Color Metadata Elements for Hardware Mapping

For standardized color grading and high dynamic range (HDR) transformations, Matroska provides dedicated video color metadata elements within the <Colour> track header (EBML ID 0x55B0). While full custom 3D LUTs reside in attachments, the <Colour> element defines baseline characteristics:

  • MatrixCoefficients (0x55B1): Defines color space conversion matrices (e.g., BT.709, BT.2020).
  • TransferCharacteristics (0x55B5): Signals the transfer function (e.g., PQ, HLG, sRGB).
  • MasteringDisplayColorVolume (0x55D0): Contains primary chromaticity coordinates and luminance ranges.

These elements provide the baseline color state, allowing rendering engines to properly interpret the input values before routing them through the custom 3D LUT stored in the attachments.

Real-Time Decoding and GPU Application Pipeline

When an MKV file containing a custom LUT is played, the media player and video renderer execute the following pipeline:

  1. Demuxing & Attachment Extraction: The demuxer identifies the video stream and parses the container's <Attachments> table to extract the LUT payload into memory.
  2. GPU Texture Upload: The renderer parses the LUT grid (e.g., a 33x33x33 or 65x65x65 3D cube) and loads the values into video memory as a 3D texture buffer using graphics APIs such as OpenGL, DirectX, or Vulkan.
  3. Shader-Based Transformation: In the display pass, after the video decoder outputs decoded YUV frames and converts them to RGB, a pixel (fragment) shader samples the 3D LUT texture. Using trilinear interpolation, the shader maps the source RGB values to the target graded color values on a per-frame basis in real time.

By utilizing EBML attachments combined with GPU shader execution, MKV enables fully reversible, real-time color grading workflows without re-encoding the original video data.

How MKV Stores Pixel vs Display Dimensions

The Matroska (MKV) container separates coded pixel resolution from presentation geometry by defining distinct metadata elements inside its video track headers. Using the Extensible Binary Meta Language (EBML) structure, an MKV file stores raw frame measurements independently of the final rendering size. This allows media players to decode video at its native pixel grid and automatically scale it to the correct aspect ratio upon playback without requiring stream re-encoding.

The EBML Video Track Architecture

In the Matroska specification, track properties are organized under the Segment > Tracks > TrackEntry hierarchy. When a track is identified as a video stream, the container includes a Video master element (EBML ID 0xE0). Within this master element, separate sub-elements handle storage dimensions and display dimensions.

Pixel Dimensions: Storage Resolution

Pixel dimensions represent the actual number of coded pixels contained within the compressed bitstream. MKV defines these using two specific EBML elements:

  • PixelWidth (EBML ID 0xB0): Defines the width of the encoded video frames in raw pixels.
  • PixelHeight (EBML ID 0xBA): Defines the height of the encoded video frames in raw pixels.

These integer values dictate the buffer size required by the video decoder to reconstruct each frame. They remain strictly tied to the encoded stream data (for example, a standard 720x480 DVD rip or a 1440x1080 HDV capture).

Display Dimensions: Presentation Scaling

To account for non-square pixels and anamorphic video, MKV provides secondary elements that dictate the target rendered output:

  • DisplayWidth (EBML ID 0x54B0): The target width at which the video should be rendered on a screen.
  • DisplayHeight (EBML ID 0x54BA): The target height at which the video should be rendered on a screen.
  • DisplayUnit (EBML ID 0x54B2): An optional parameter indicating how DisplayWidth and DisplayHeight should be interpreted (e.g., 0 for pixels, 1 for centimeters, 2 for inches, or 3 for aspect ratio). By default, this value is 0 (pixels).

If DisplayWidth and DisplayHeight are omitted, the container assumes square pixels, rendering the video at the values specified by PixelWidth and PixelHeight.

How Players Process the Data

During playback, the media pipeline functions in two distinct stages:

  1. Decoding: The video decoder uses PixelWidth and PixelHeight to allocate memory buffers and decode the compressed macroblocks into raw image frames.
  2. Rendering: The video renderer reads DisplayWidth and DisplayHeight from the MKV container header. It calculates the Pixel Aspect Ratio (PAR) or Display Aspect Ratio (DAR) and stretches or compresses the decoded frame to match the target display dimensions.

Because these values exist as lightweight container metadata rather than hardcoded video stream headers, users and authoring tools can modify the display aspect ratio instantly using header editing tools without touching or recompressing the underlying video stream.

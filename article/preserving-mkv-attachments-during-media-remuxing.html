Preserving MKV Attachments During Media Remuxing

Remuxing an MKV (Matroska) file involves restructuring or transferring container streams into a new file without re-encoding the underlying video and audio data. Media converters preserve embedded attachments—such as subtitle fonts, cover artwork, and contextual metadata—by reading the original container's dedicated attachment elements and copying their exact binary data directly into the destination file.

The Structure of MKV Attachments

The Matroska multimedia container is built on EBML (Extensible Binary Meta Language), a binary format conceptually similar to XML. Within an MKV file, attachments reside in a dedicated master element separate from video, audio, and subtitle tracks.

Each embedded attachment contains specific descriptors:

  • File Name (FileName): The original name of the attached asset (e.g., font_style.ttf).
  • MIME Type (FileMediaType): The data format identifier (e.g., application/x-truetype-font or image/jpeg).
  • Binary Data (FileData): The raw, uncompressed payload of the file.
  • File Description (FileDescription): Optional metadata explaining the purpose of the attachment.
  • File UID (FileUID): A unique numerical identifier within the container.

How the Remuxing Process Copies Attachments

Remuxing operates at the container layer rather than the codec layer. When preserving attachments, a media converter executes three core steps:

1. Demuxing the Container

The converter’s demuxer parses the EBML tree of the input MKV file. It identifies track headers, cluster packets (audio/video frames), and the Attachments cluster. Rather than processing the attachments through a decoder, the parser reads the raw binary data stored in the FileData elements directly into memory buffers.

2. Stream and Attachment Mapping

During standard remuxing, media converters map data streams from the source to the target container. Advanced converters identify attachments as distinct stream or metadata types (often classified as "attachment streams"). The engine flags these elements for a direct bitstream copy, bypassing any compression or modification algorithms.

3. Muxing to the Target File

The muxer writes the target MKV file by generating a new EBML header, copying the audio/video clusters, and reconstructing the Attachments block. The binary payload, MIME types, and file names are written into the new container exactly as they appeared in the source file, maintaining complete data integrity.

Software Implementation

Different remuxing tools manage attachment preservation through specific container handling methods:

  • MKVToolNix (mkvmerge): Designed specifically for the Matroska format, mkvmerge treats attachments as primary container components. By default, it preserves all attached files during remuxing unless a user explicitly applies the --no-attachments flag.
  • FFmpeg: FFmpeg treats attachments as independent streams (often identified with the stream specifier :t). When remuxing with the stream copy command (-c copy), users must ensure the stream mapping command includes attachment streams (e.g., using -map 0 or -map 0:t?) so the muxer writes them into the output file.

Limitations Across Different Containers

Attachment preservation is dependent on container support. While remuxing from MKV to MKV retains embedded attachments natively, remuxing MKV to a container like MP4 requires the converter to handle attachments differently. MP4 does not use EBML and has limited native support for arbitrary file attachments like custom fonts, which often forces converters to either discard the attachments or convert cover art into standard MP4 metadata tags.

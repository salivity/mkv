Preserving HDR Metadata When Compressing MKV Files

Preserving High Dynamic Range (HDR) color metadata during MKV compression requires transcoders to accurately extract, process, and re-inject critical color parameters rather than discarding them as auxiliary data. When compressing high-bitrate HDR sources into smaller MKV files, transcoders bridge container-level Matroska properties and bitstream-level codec instructions. By parsing static or dynamic metadata from the source and passing explicit encoding flags to modern encoders like x265, SVT-AV1, or libvpx, transcoders ensure the compressed stream retains proper luminance ranges, wide color gamuts, and tone-mapping instructions for HDR-capable displays.

The Two Layers of HDR Metadata in MKV

To maintain HDR integrity, a transcoder must handle metadata at both the container level and the elementary bitstream level.

  1. The Bitstream Level (VUI and SEI): The video stream itself (such as H.265/HEVC or AV1) contains Video Usability Information (VUI) and Supplemental Enhancement Information (SEI) messages. These messages carry essential parameters directly to the video decoder.
  2. The Container Level (Matroska Elements): The MKV specification includes specific track elements under the Colour header (such as MatrixCoefficients, BitsPerChannel, TransferCharacteristics, Primaries, and MasteringMetadata) that allow players to configure display pipelines before decoding frames.

Extraction and Demuxing

During the initial demuxing phase, the transcoder's demuxer (typically powered by libraries like FFmpeg's libavformat) reads both the MKV container headers and the input elementary stream. It identifies the fundamental HDR parameters:

  • Color Primaries: Usually ITU-R BT.2020.
  • Transfer Characteristics: Usually SMPTE ST 2084 (PQ) or ARIB STD-B67 (HLG).
  • Matrix Coefficients: BT.2020 non-constant luminance (bt2020nc).
  • Mastering Display Color Volume (SMPTE ST 2086): X/Y chromaticity coordinates for primary colors, white point coordinates, and minimum/maximum luminance values.
  • Content Light Level (CTA 861.3): Maximum Content Light Level (MaxCLL) and Maximum Frame-Average Light Level (MaxFALL).

Encoder Parameter Forwarding

Video compression is lossy and reconstructs pixel arrays, meaning standard compression algorithms will strip bitstream SEI messages unless explicitly instructed to retain them. Transcoders preserve this data by automatically translating the extracted values into encoder-specific command-line arguments.

For example, when compressing to an HEVC stream using the x265 encoder, the transcoder passes arguments such as:

  • hdr10=1 (enforces strict HDR10 compliance and signaling)
  • colorprim=bt2020
  • transfer=smpte2084
  • colormatrix=bt2020nc
  • master-display=G(x,y)B(x,y)R(x,y)WP(x,y)L(max,min)
  • max-cll=MaxCLL,MaxFALL

This ensures the newly encoded Network Abstraction Layer (NAL) units contain the exact color transformation equations and luminance limits of the source.

Handling Dynamic Metadata

Dynamic HDR formats—such as HDR10+ (SMPTE ST 2094-40) and Dolby Vision (SMPTE ST 2094-10)—change luminance mappings on a frame-by-frame basis.

  • HDR10+: Transcoders extract the dynamic JSON metadata stream during demuxing and feed it to the encoder to be written into per-frame SEI messages.
  • Dolby Vision: Transcoders extract the Reference Processing Unit (RPU) metadata. If transcoding between compatible HEVC profiles, the RPU is parsed, aligned with the newly encoded frames, and interleaved back into the bitstream without altering the dynamic tone-mapping curves.

Re-Muxing into the Output MKV

After the compression engine outputs the newly compressed elementary stream with embedded SEI/VUI data, the transcoder’s muxer constructs the final MKV container. The muxer reads the metadata from the encoded stream and writes matching Matroska Colour track elements. Writing this data to both the MKV headers and the internal bitstream ensures maximum compatibility across software media players, hardware media streamers, and television displays.

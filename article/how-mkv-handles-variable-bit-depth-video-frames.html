How MKV Handles Variable Bit Depth Video Frames

The Matroska (MKV) container handles variable bit depth video frames primarily by acting as a transparent passthrough for codec-level dynamic configuration changes or by utilizing multi-segment linking. While the MKV specification includes track-level metadata fields for bit depth, dynamic changes across individual frames within a single continuous track are governed by the elementary video stream rather than the container itself.

Track-Level Metadata vs. Bitstream Signaling

At the container level, an MKV file defines video properties inside the TrackEntry master element. Within this element, the Video sub-element contains fields such as BitDepth and Colour information.

These container-level headers are generally static and define the baseline expectations for the entire track. MKV does not alter its primary track header per frame. When a video stream switches bit depth (for example, from 8-bit to 10-bit color), the MKV container stores each frame sequentially within standard SimpleBlock or BlockGroup elements without modifying the top-level track header on the fly.

In-Band Dynamic Codec Switching

For variable bit depth to function within a single MKV track, the embedded video codec (such as AV1, HEVC/H.265, or VP9) must support in-band sequence parameter updates.

  1. Sequence Headers: The video encoder injects a new sequence header—such as a Sequence Parameter Set (SPS) in HEVC or a Sequence Header OBU in AV1—directly into the bitstream payload before the keyframe (I-frame) where the bit depth change occurs.
  2. Container Passthrough: The MKV muxer places these updated packets into MKV blocks like any other frame data. The container does not need to parse or validate the bit depth change; it simply delivers the raw bitstream to the demuxer.
  3. Decoder Reconfiguration: During playback, the demuxer splits the MKV container and sends the payload to the video decoder. The decoder reads the in-band sequence header, halts the current decoding pipeline, reallocates internal frame buffers to accommodate the new bit depth (e.g., switching from 8-bit YUV420p to 10-bit YUV420p10), and resumes playback.

Multi-Segment Linking and Ordered Chapters

When dealing with video segments that cannot be seamlessly switched within a single continuous elementary stream, MKV handles variable bit depth using Segment Linking and Ordered Chapters.

  • Segment Linking: MKV allows multiple distinct files (segments) to be logically chained together. Each segment contains its own independent TrackEntry with unique BitDepth definitions and codec initialization data (CodecPrivate).
  • Seamless Timeline Assembly: The master MKV file uses an ordered chapter table to instruct the player to switch between separate segments at specific timestamps. This enables a container-driven transition between an 8-bit segment and a 10-bit segment without requiring in-band bitstream reconfiguration.

Playback and Hardware Limitations

Although MKV accommodates variable bit depth delivery through bitstream passthrough and segment linking, real-world playback depends heavily on decoder capabilities:

  • Hardware Decoders: Fixed-function hardware decoders often fail or drop frames during mid-stream bit depth changes because memory surfaces are allocated statically at playback initialization.
  • Software Fallbacks: Software decoders (such as FFmpeg/libavcodec) handle dynamic bit depth shifts more reliably by tearing down and reinitializing the rendering context when a sequence header change is detected.

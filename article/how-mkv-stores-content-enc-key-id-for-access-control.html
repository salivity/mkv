How MKV Stores ContentEncKeyID for Access Control

The Matroska (MKV) container uses an Extensible Binary Meta Language (EBML) structure to implement selective stream access control by attaching cryptographic metadata directly to individual tracks. Through the ContentEncKeyID element, an MKV file stores a unique binary identifier for the decryption key required by a specific audio, video, or subtitle stream. This overview explains the structural placement of ContentEncKeyID within the Matroska header hierarchy, its relationship with external Key Management Systems (KMS), and how it enables granular, per-track encryption.

The EBML Structural Hierarchy

Matroska organizes data into a nested tree of EBML master elements. Track-level encryption parameters reside within the file header rather than inside the raw media payloads. The storage hierarchy for access control metadata follows this path:

  • Segment (0x18538067): The root container for all multimedia data.
    • Tracks (0x1654AE6B): Contains definitions for all streams in the file.
      • TrackEntry (0xAE): Defines a single track (e.g., 4K video, stereo audio, commentary).
        • ContentEncodings (0x6D80): Wraps all encoding, compression, and encryption settings.
          • ContentEncoding (0x6264): Defines a specific operation applied to the track.
            • ContentEncryption (0x5035): Specifies cryptographic parameters.
              • ContentEncKeyID (0x47E1): Contains the key identifier binary payload.

The Role and Format of ContentEncKeyID

The ContentEncKeyID element (EBML ID 0x47E1) is a binary element containing a distinct key identifier, often a 16-byte UUID (similar to Common Encryption / CENC Key IDs).

Matroska's security architecture strictly separates the Key ID from the Content Encryption Key (CEK):

  • Identification vs. Secret: The MKV file never stores the actual decryption key in plaintext inside ContentEncKeyID. Instead, it stores an identifier that a media player passes to a Digital Rights Management (DRM) client or license server.
  • Cryptographic Association: Alongside ContentEncKeyID, the ContentEncryption master element defines the cipher suite via ContentEncAlgo (e.g., AES-128) and the encryption mode via ContentCipherMode (e.g., CTR or CBC).

Mechanics of Selective Stream Access Control

Because ContentEncKeyID is scoped inside individual TrackEntry elements, MKV allows content creators to apply independent access policies to different streams within the same container file:

  1. Independent Key Assignment: A video track (Track 1) can contain a ContentEncKeyID pointing to a premium tier key, while a standard-definition video track (Track 2) uses a separate Key ID.
  2. Heterogeneous Protection: Secondary tracks, such as standard stereo audio or public subtitles, can omit the ContentEncodings element entirely, remaining unencrypted and openly playable.
  3. Targeted Key Resolution: During playback, the demuxer reads the TrackEntry for a requested stream, extracts the ContentEncKeyID, and requests authorization only for that specific ID. If a user only has rights to access the audio track, the license server only returns the key matching the audio ContentEncKeyID, leaving the encrypted video data inaccessible.

When reading media frames (SimpleBlock or BlockGroup), the demuxer utilizes the retrieved key corresponding to the track's ContentEncKeyID along with any initialization vectors stored in ContentEncAESSettings to decrypt the raw frame payloads.

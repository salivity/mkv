Why Media Servers Transcode MKV Files in Browsers

Media servers frequently transcode Matroska (MKV) video files when streaming to web browser clients due to native compatibility limitations. While MKV is a popular and flexible multimedia container, standard web browsers are not built to natively parse the MKV format or decode certain proprietary audio, video, and subtitle codecs packed inside it. To ensure smooth playback, media servers such as Plex, Jellyfin, and Emby automatically convert the container, audio, or video into browser-friendly formats like MP4 or WebM on the fly.

The MKV Container vs. Browser Standards

An MKV file is not a video format itself, but a container that holds video, audio, subtitle, and metadata streams. Web browsers rely on the HTML5 <video> standard, which natively prioritizes MP4 and WebM containers. Because most browsers lack native demuxers to read and unpack the MKV container format directly, the media server must intervene to make the file readable for the web client.

Video and Audio Codec Incompatibilities

Even if a browser could parse the container, the individual streams inside the file might not be supported:

  • Audio Codecs: High-end multi-channel formats commonly stored in MKVs—such as DTS, Dolby TrueHD, or AC3—rarely have native decoding support or licensing in web browsers. Browsers typically require stereo AAC or Opus.
  • Video Codecs: While H.264 (AVC) is universally supported, higher-efficiency codecs like HEVC (H.265), AV1, or 10-bit color profiles may lack hardware acceleration or software support in specific browsers.

Subtitle Rendering and "Burning"

MKV files often contain advanced subtitle tracks, such as PGS (bitmap image subtitles) or ASS/SSA (styled script subtitles). Standard HTML5 video players can only natively render basic WebVTT or SRT text subtitles. When a user enables incompatible subtitles in a browser, the server must perform a full transcode to "burn" the text or images directly into the video frames.

Remuxing vs. Full Transcoding

Depending on what causes the incompatibility, the server performs one of two processes:

  • Direct Stream (Remuxing): If the video and audio codecs are already compatible (e.g., H.264 video with AAC audio) and only the MKV container is unsupported, the server repackages the streams into an MP4 or HLS container without re-encoding the video, using minimal CPU power.
  • Full Transcode: If the video codec, audio codec, or subtitle format is incompatible, the server fully decodes and re-encodes the media into supported formats, consuming significant server processor or GPU resources.

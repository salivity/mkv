How MKV Containers Store Custom Subtitle Styles

The Matroska (MKV) container stores custom subtitle styles and overrides default media player formatting by encapsulating advanced text-based script formats alongside embedded font attachments within its structural stream. By combining the styling capabilities of the Advanced SubStation Alpha (ASS) format with Matroska's native file attachment system, content creators can dictate exact typography, positioning, colors, and animations rather than relying on the client player's basic fallback renderer.

Advanced SubStation Alpha (ASS/SSA) Tracks

The core mechanism for custom styling inside an MKV container is the use of ASS (.ass) or SSA (.ssa) subtitle streams. Unlike basic formats like SRT that only contain timing and raw text, ASS is a complete script-based format. Within the MKV file, an ASS track includes:

  • The Script Info Section: Defines global properties, canvas resolution (ScriptType, PlayResX, PlayResY), and aspect ratio matching the underlying video.
  • The Styles Section ([V4+ Styles]): Defines specific named styles with parameters such as font family, font size, primary/secondary/outline/shadow colors (in hexadecimal format), alignment, margins, and border styles.
  • Dialogue Events with In-line Overrides: Individual lines of dialogue reference the predefined styles, but can also include inline override tags (such as {\pos(x,y)}, {\c&H0000FF&}, {\fad(200,200)}, or {\an8}). These tags allow precise, frame-by-frame manipulation of text appearance and screen placement.

Matroska Font Attachments

Custom styling fails if the playback system does not have the specified fonts installed. MKV solves this through its binary attachment feature via the Extensible Binary Meta Language (EBML) structure.

Font files (TrueType .ttf or OpenType .otf) are embedded directly into the MKV file as attachments (AttachedFile elements) rather than separate streams. Each attachment includes:

  1. File Name: The name of the font file.
  2. MIME Type: Identifiers such as application/x-truetype-font or font/otf.
  3. Binary Data: The raw font file data.

When a media player opens the MKV, its subtitle rendering engine reads these attachments into memory without requiring them to be installed onto the host operating system.

How Renderers Process and Enforce Styles

Modern media players utilize dedicated subtitle renderers—predominantly libass or VSFilter/DirectVobSub—to display MKV subtitle tracks.

When playback begins, the rendering pipeline operates as follows:

  1. Font Indexing: The engine indexes all embedded fonts found in the MKV attachment headers into a private font provider cache.
  2. Script Parsing: The subtitle stream is parsed, matching the Fontname attributes in the ASS style definitions with the indexed in-memory fonts.
  3. Canvas Scaling: The renderer scales the subtitle canvas to match the video display resolution based on the PlayResX and PlayResY headers.
  4. Composition: The styled vector shapes and text are rasterized on a dedicated graphic plane directly over the video stream, bypassing standard player settings for font size, color, or placement.

Bitmap Subtitles: PGS and VobSub

In addition to text-based ASS scripts, MKV containers can store graphical bitmap subtitle formats such as Blu-ray PGS (.sup) or DVD VobSub (.sub/.idx). These formats do not store text or style rules; instead, they store pre-rendered, transparent image overlays. Because they are visual images mapped directly to specific timestamps and coordinate planes, the media player cannot apply default font settings, ensuring exact visual fidelity by design.
